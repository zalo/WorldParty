# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

WorldParty is a multiplayer sandbox for building interactive worlds, similar to Garry's Mod. It uses three.js for 3D rendering and PartyKit for real-time multiplayer networking. Players can carve/add voxel terrain using CSG (Constructive Solid Geometry) operations and spawn 3D models (GLB files) by URL.

## Commands

```bash
npm install          # Install dependencies
node tools/gen-fortwar.mjs   # Build the Fort War level (assets/worlds/fortwar.json) from CSG primitives; open ?room=<name>&import=/assets/worlds/fortwar.json
npm run dev          # wrangler dev + esbuild watch (tools/dev.mjs); serves the site and rooms at localhost:1999 (PORT=... to change)
npm run build        # Assemble the static site in ./public/ (index.html, assets/, bundled dist/main.js and the vertex GI worker dist/giWorker.js) via tools/build-site.mjs
npm run deploy       # Build, then `wrangler deploy` the Worker, Durable Object and site to Cloudflare (https://worldparty.makeshifted.workers.dev)
node tools/import-world.mjs model.glb --name castle --size 60   # GLB -> destructible world manifest in assets/worlds/
node tools/profile/build.mjs && node tools/profile/csg.mjs assets/worlds/castle-exact.json [chunkKey] [carves]   # time a carve stage by stage against the real server class in Node (also summary.mjs, cook.mjs) (also tick.mjs: where a tick's time goes; replay.mjs: carves recorded from a client)
```

Open `?room=<name>&import=/assets/worlds/castle.json` (or call `main.importWorld(url)`) to upload a manifest into a room; the room's terrain, entities and world config are replaced.

Hosting is a Cloudflare Worker (`wrangler.jsonc`): the room server is a Durable Object class bound as `Main` and routed by [PartyServer](https://github.com/threepointone/partyserver)'s `routePartykitRequest` (so clients still use `/parties/main/<room>`), and everything else is served from `public/` as static assets (SPA fallback). The client JS is bundled by esbuild from `src/main.js` into `public/dist/`; `PARTYKIT_HOST` is injected as a global and is only the fallback host for pages not served over http(s). Rooms persist in SQLite-backed Durable Object storage (2 MiB per value; chunk bytes are still split into parts). The hosted PartyKit platform shut down in October 2026; `partykit.json` is gone.

## Architecture

### Client-Server Split

- **`src/server.js`** - Room server: a PartyServer `Server` (Durable Object) plus the Worker `fetch` export. Owns the authoritative ECS world, PhysX simulation, and terrain. Ticks at 30Hz, broadcasting `partialupdate` (dirty components only) and a `fullupdate` every 10s (without `FragmentMesh`, which never changes after creation; the one sent on connect has everything). Persists entities and chunks under per-key storage (`ent:<id>`, `chunk:<x,y,z>`; legacy numeric chunk keys are migrated on load) every 5s and on disconnect.
- **`src/main.js`** - Client entry point. Mirrors the server's entities into a local ECS world, runs render/interpolation systems, hosts the local `PlayerController`, the terrain mirror, tools, and spawn menu. Connects via `PARTYKIT_HOST` (injected by bundler).

### Entity Component System

See `docs/ecs.md`. `src/ecs/World.js` is shared by both sides. Entities are id + plain-JSON components; names starting with `$` are transient runtime handles (PhysX actors, three.js meshes) that each host rebuilds. Server systems live in `src/server/Physics.js`, client systems in `src/client/systems.js`. Spawning, loading from storage, and (future) migrating between Durable Objects are all "create the entity, let systems materialize it".

### Key Modules

- **`src/World.js`** - Three.js WebGPU renderer, camera, sun light, the sky setup, and two ways to draw a frame (`renderFrame`): on desktop the post-processing pipeline (scene pass into MRT targets, TRAA, optional SSGI with `?gi=1`); on mobile (or `?traa=0`, or `?direct=1`) `renderer.render` straight to the canvas with 4x MSAA, which still tone maps (ACES, exposure 0.42) and converts to sRGB in the renderer's output pass, so it matches the pipeline minus the temporal AA (measured: mean colour equal to three decimals). TRAA blurred a phone's small frame and the MRT targets plus TRAA history are a lot of bandwidth for a tiled GPU. Mobile renders at 1 CSS pixel per pixel (it was a quarter of the device ratio, 0.75 on a DPR 3 phone: most of the blur; `?dpr=<n>`), is capped at 60 fps in `Main.update` (`?fps=<n>`, 0 uncapped; 120 Hz phones otherwise render twice as often), and runs no probe grid when vertex GI runs (with r186's capture each probe bake was six renders of the scene: ~13 ms of CPU on a 4x-throttled desktop plus the GPU, every few frames for minutes after load and after every dig, which was the hitching on phones; the batched capture, see ProbeLighting, is far cheaper but has not been tried on a phone); moving objects there take the sky's image based light at `MOBILE_ENVIRONMENT` (3), `?probes=1` brings the grid back (then a coarser grid, one probe at a time within a 2 ms budget). `?gputime=1` turns on GPU timestamps (`renderer.resolveTimestampsAsync`). Frame rates measured in the headless Weston browser are capped near 30 fps by its presentation path even for an empty scene; compare CPU times there.
- **`src/client/ProbeLighting.js`** - Irradiance probe grid (three `LightProbeGrid`, WebGPU only) over the world bounds, baked on the GPU a few probes per frame nearest the camera first (the frame's dirty probes in one bake call, `runs`; at most `MAX_PER_FRAME` = 8 with the batched capture, one batched render, ~1 ms of GPU on an RTX 4090: the CPU-time budget had let it take 64 a frame, 5 ms of GPU, a dropped frame on every rebake after a dig on a 240 Hz display or a slower GPU). The grid class is `src/client/vendor/LightProbeGrid.js`, three's from [PR #34909](https://github.com/mrdoob/three.js/pull/34909) (open as of 2026-10-19; drop the copy once a release has it): eight probes per render through one 48-view `ArrayCamera` instead of a `CubeCamera` per probe (six renders and a submit each), and an exact solid-angle SH projection; its two core dependencies landed after r186 but do not matter here (no point or spot lights, one `ArrayCamera`). `?probebake=cube` goes back to r186's class. The batched capture has no per-view culling, so every object is drawn in all 48 views; what makes it pay is what captures draw: the terrain as its collision geometry carrying each corner's GI record (`TerrainMirror.captureView`, a few merged pieces of 8x4x8 chunks rebuilt where a chunk changed; Twin Forts: 11k triangles against 190k refined), and no bodies or players (`Main.attachProbes`: they move on and would leave their shading baked in; Fort War's six supply crates were 32k triangles). `?probeproxy=0` captures the refined batches instead. Moving a probe out of solid (`bakePosition`) raycasts only the chunks within reach (all 356 of Twin Forts' cost 0.45 ms per probe). Measured on this desktop for Twin Forts' 3045 probes: the whole grid bakes in 6-8 s (54 s with r186's capture of the refined terrain), 0.16-0.19 ms of CPU per probe (1.94), 141k triangles per probe (560k); against r186's capture the probes agree to 0.08% (median; worst 3.75%) with vertex GI off, and with it on the coarse capture reads 4.5% darker on average (p90 16%: a large coarse triangle carries the darkness of its corners in the creases across its face). `TerrainMirror.onChunkChanged` passes the bounds of what a carve changed (`changedBox`: the vertices one version has and the other lacks) and only the probes at the corners of the cells it overlaps are rebaked (it was a step beyond the whole 10 m chunk, ~125 probes, six scene renders each, per drill bite). `?probes=0` disables it; `?probes=show` draws a sphere per probe shaded by what it baked, where it baked from (three's `LightProbeGridHelper` with an unlit colour node; it must stay on layer 0, which is all the scene pass renders, and is hidden while baking). Probe positions lie on a world lattice (multiples of the 6 m step) so that when the band grows (`Main.probeBounds`: the union of chunk rows ever held, never shrinking) the new grid copies the old grid's baked rows (a 3D atlas texture copy) and bakes only the new ones: before that, every refit (walking into the vault was enough) threw the whole bake away and the grid never finished. A probe that lands inside solid (the lattice row at y=0 is 10 cm under the plaza) sees sky through every back-face-culled surface and never the sunlit sand; `bakePosition` moves it just outside the nearest surface (BVH raycast against `occluders`, the chunk group) first. The sampling node is a subclass with a 1 m normal offset instead of three's half-spacing (3 m read the probes behind a wall). What the probes capture decides whether they mean anything: a capture renders surfaces with the sky's image based light, which knows nothing about occlusion, so while the scene ran it at 7x (and then 1.75x as a floor) a probe in the vault saw walls lit like the courtyard, the vault looked like daylight and the probes looked like nothing. Captures use `bakeEnvironment` (0.35) and, once baked, the scene's image based light drops to `environmentFloor` (0.2; `environmentUnbaked` 2.5 stands in before), so occlusion lives in the probes; `ambient` (10) multiplies the probe light (this sky's shade is ~1:80 of the sun physically; measured on the red courtyard, sunlit stone 62/255 against a shaded top 20). `?ambient=`, `?envfloor=`, `?bakeenv=` tune them. Known leak: trilinear interpolation between a probe above a sewer ceiling and one below lights the ceiling with courtyard light. An unbaked probe is black, so the grid's intensity follows the baked fraction. A failed bake puts its probes back and pauses; it never pretends to be done. Big worlds are capped at 4000 probes (the step coarsens).
- **`src/client/TerrainGI.js` + `giCore.js`** - Vertex GI on the terrain (WebGPU only; `?vgi=0` off): the indirect light (sky, sun bounce, further bounces; direct sun stays on the cascades and the glow rocks on GlowLighting) accumulated into the vertices of a refined render mesh, a budget of rays per frame (`?girays=`, 32768 desktop / 4096 mobile). Chosen over lightmap UVs because only slowly varying indirect light is baked: no charts or atlas to repack when a carve cuts a new surface, no seams, and far fewer sample points. The CPU side runs in a Web Worker (`giHost.js` hosting giCore, started from `giWorker.js`, its own bundle `dist/giWorker.js` next to `main.js`; on the main thread if a worker cannot start): refinement, records, adaptive splits, scheduling, light seeding (with its own BVH per chunk for sight checks) and the crystals' bookkeeping. On the main thread a readback's adaptive passes had stalled frames for up to 0.4 s on this desktop (36 passes refined 174 chunks: each pass re-refined its neighbours at once); now a pass only marks chunks, each marked chunk is refined once, 6 ms of that per frame message, and the main thread's frame stays under 9 ms (p99 7). The worker also packs the GPU BVH (`BVHComputeData` over its own chunk BVHs, each corner carrying its record and the triangle's albedo, sent by the main thread) and sends the buffers: that repack had cost 22-32 ms of a 4x-throttled main thread once a second while digging. The main thread writes them into the buffers the passes already bind when they fit (allocated with half again the room), so a dig does not rebuild the passes either (three's node building, ~14 ms throttled); only a buffer that has to grow does. With vertex GI the terrain takes no image based light (`TerrainNodeMaterial.setupEnvironment`: the gathered light has the sky in it, with occlusion), and where there is no probe grid an unsampled vertex stands in with half the open sky (`giFallback`). The main thread posts each changed collision geometry (with its hidden-cap flags, albedo and a carve's box), receives refined meshes and per-frame work packages (jobs, glow jobs, crystal buffer writes; every message carries the new records' uploads and init/knock ops first), and keeps one frame request in flight. TerrainMirror's `deferDraw` keeps a carved chunk's previous drawing until its refined mesh is back (at most 250 ms), so the worker's frame or two of latency never shows the probe grid's light on a dig. CPU side (`giCore.js`): each chunk's collision geometry is subdivided so no edge is longer than `maxEdge` (2 m, 3 on mobile; Twin Forts' triangles average 4 m²) plus edges whose two ends' light differed by more than `contrast` at 64 and 192 samples (`splitEdges`, down to `minEdge` 0.4); the rule looks only at the edge, so neighbours (also across chunks) split alike and there are no T-junctions. A vertex's light is a record keyed by position + normal, shared across materials and chunks, so seams are continuous and a carve keeps every sample of the surfaces it did not touch; records near a carve are knocked back to 12 samples (see below). Triangles on a chunk plane are skipped when hidden (facing into the chunk, against the next chunk's own cap, or out of the world box: Twin Forts' outer skin is ~45k m²); the server's cull mask already removes most caps. GPU side: three-mesh-bvh 0.9.16's `BVHComputeData` packs proxy meshes sharing the collision geometries (and their BVHs, so only a changed chunk's BVH is rebuilt; `update()` still repacks everything, so it runs at most once a second and a changed chunk is not sampled until it is in) with a `surface` attribute (corner record, albedo from the material colour and the texture layer's mean, `TerrainTextures.averages`); a compute pass traces one cosine-distributed ray per scheduled record (`raycastFirstHit`): sky gradient fitted to the atmosphere's irradiance and horizon on a miss, black on a back face, else albedo times (sun with a shadow ray + the hit triangle's corner records interpolated), so each pass adds a bounce; an exponential average past 256 samples. The gather may bind at most 8 storage buffers (WebGPU's default; phones), hence one buffer for record position+normal and the sun/sky as uniforms, and it is rebuilt after every BVH update (the proxies resolve at build time). Records live in GPU buffers (2^18, 2^17 on mobile); new ones are initialised by an ops pass. A new record copies the light of gathered records it can see, at full display weight (`GICore.seed`: the ends of the edge it splits, else the two nearest within 3 m facing its way, found in a 1 m spatial hash of records and checked for sight against the chunk BVHs); one a carve just exposed keeps 0.6 of what it copies (it lies deeper than what it copies from), and with nothing in sight starts dark. Before this a fresh surface started empty, so the shader showed the probe grid, whose probes deep in rock bake from inside solid and see sky: a tunnel dug out of the vault came in at 50/255 and settled at 26; now 34 and 30. Records near a carve are knocked back only to `weightAt` samples, for the same reason (fewer brought the probes back on the walls around every dig). TerrainMirror exposes the region a carve changed while it rebuilds the chunk (`changing`). The terrain material reads its vertex's record in the vertex stage (`rec` attribute, -1 = none) and adds mean * min(1, samples/12) * the probes' `ambient` through `setupLightMap` (`TerrainNodeMaterial`); the probe grid fades out by the same weight (`ProbeGridNode`), so props and players keep the probes and new surfaces show them until gathered. A record needs a normal: a zero-area triangle's corner (zero normal) or the mean of two opposite normals gets none (`giCore.refine` `hasNormal`), and both passes skip one without (a NaN ray direction is rejected by no BVH box, so the ray walked the whole tree: 16 ms for one ray on an RTX 4090, and a gather that drew such records took 11-90 ms). Measured on this desktop with GPU timestamps (`?gputime=1`), Twin Forts steady state: render 2.5 ms, GI compute 1.2 ms per frame (a dig frame ~7 ms); ~0.5 ms main-thread CPU per frame, ~0.6 s of refinement for Twin Forts as its chunks arrive (adaptive passes add a second or so over the first minute); the sewer middle is physically near black (multi-bounce light from the gorge dies within metres; the probes had been leaking courtyard light through its ceiling), the crystals light it. Glow rocks are baked into the same vertices (`TerrainGI.setRock`, fed by GlowRockRenderSystem through GameClient's `glowSink`): each crystal is a point light standing 35 cm out of the wall along the normal of the terrain surface nearest it (averaging the directions rays could travel put many inside the rock), linked to the records within 3.5 m (each record keeps its 7 nearest crystals); a glow pass computes, once per record whenever a crystal near it appears, changes or goes or the terrain around it changes, the crystals' light with one shadow ray each and the glow volume's falloff, into a second vec4 per record. The gather reads it as part of the cached light at its hits, so crystal light bounces, and adaptive splits see it (pools get finer vertices). Crystals are placed and baked again after the next BVH update (the packed BVH may not yet have the dig that exposed them). No per-frame cost once baked and nothing switching with the camera; only terrain receives it (players and props got the glow volume's light before). `glowGain` 3.0 (`?glow=<n>` sets n/10). `?tridebug=7` shows the gathered light unlit (with the crystals'), `8` its weight. With `?batch=0` the collision meshes are drawn and get only their corners' light (`TerrainMirror.setCoarseRecords` writes each corner's record into the collision geometry's `rec` attribute, for the probe captures).
- **`src/client/terrainMaterial.js`** - The terrain material for chunks and fragments: per-face vertex colour, or a layer of the world's texture array (`TerrainTextures`) sampled triplanar from the world (chunks) or local (fragments) position when the material has a `scale` (metres per tile), else by UV (imported worlds' own textures); `tint` multiplies by the colour. The palette materials carry CC0 Poly Haven textures (`assets/textures/`). The layer index attribute is rounded, not truncated: interpolation lands a hair under the integer on some pixels and truncation drew the previous layer in stripes. `?tridebug=1..6` shows weights, layer, single projections, unlit. `TerrainTextures` disposes the array texture before resizing it (the GPU texture is created at the placeholder's size otherwise and every upload fails validation, leaving textures white). A tint only darkens: a surface that reads black in full sun is a dark texture (Fort War's `dark_rock.jpg` averaged 0.015 linear before it was lightened in the asset), not the lighting; `identify -format "%[fx:mean]"` on the texture settles it.
- Terrain normals are per face, blended across adjacent faces of `smooth` materials (dirt, sand, grass, snow; `materials.js`) within 70°, so carved craters and tunnels read as curved while built stone keeps hard edges (`buildTerrainGeometry`; vertices at one position are found through a numeric hash at 0.1 mm with an exact compare: the string keys it used were the slowest step of a carve on a phone). Chunk meshes are never simplified after a carve, so digging the same place over and over grows them without bound (a test room carved hundreds of times in one tunnel reached 470k triangles per chunk, and loading it took seconds); a round's reset restores them in Fort War. The server's own sphere brushes (`carveSphere`): explosions carve an 80-face icosphere simplified at 0.1 m, the drill (`carveCapsule`) the hull of two 320-face ones at 0.02 m so its tunnels read as round (`csg` messages may pass `tolerance`; client brushes default to 0.1).
- Shadows are three r186's `SunLight` (`src/World.js`): two view-fitted cascades in one atlas (4096² each on desktop, 2048² mobile; the near cascade reaches ~33 m at 2 cm texels, the far one `CSM_FAR` = 130 m at ~7 cm, blended over a fade band and texel snapped), 5 tap PCF (`PCFSoftShadowMap` no longer exists in r186) rotated per pixel by a noise TRAA resolves (radius 1.5 texels; 1 on the direct path, where the rotation would show as dither). The light's position is its direction (no target; `DayCycle` sets it). Terrain casts with its front faces (`terrainMaterial.js` `shadowSide`): three's default back faces stored the far side of every wall, which met the lit surface within the bias at wall bases and sewer ceiling edges and drew a bright line of leaked light there; with the sun-facing surface in the map nothing behind a wall is within its thickness of the stored depth, so `bias` is 0 and only `normalBias` 0.06 keeps lit surfaces off their own map. `?csm=0` is the old single 180 m box. The `CSMShadowNode` addon (`?csm=old`, kept for the record) drew nothing here because it clones the sun's `LightShadow` per cascade at the first material build, which happens inside a probe bake that has just set `autoUpdate=false, needsUpdate=true` on every shadow casting light, and `LightShadow.copy` carries both flags: the cascade maps rendered once and never again (`World.update` now undoes it; `tools/csm-test.js` is the bare page that proved the pipeline itself was fine). The probe bake swaps a `SunLight` for a fitted plain light while it captures (`LightProbeGridUtils`). Screen-space GI is off by default (`?gi=1`); the probe grid carries the bounce light. A thin sky-coloured haze (`scene.fogNode`, 12% at 100 m, `?fog=0|<k>`) separates the far fort.
- **`src/sky/`** - Physically based sky ported from tidewater's three.js/TSL version (commit `3dd589b` there): `Atmosphere` (Hillaire LUTs in compute, sun transmittance / sky irradiance readback; Mie scale 2 and a sandy ground albedo, which lift the hemisphere irradiance from (0.10, 0.21, 0.46) to (0.16, 0.28, 0.53) and take the navy out of the shade), `Sky` (sun disk, stars, moon; no clouds yet; below the horizon the LUT holds only the in-scatter down to the planet, so `_background` adds a sunlit plain there, otherwise the ground between a level's edge and the horizon is a black band), `Environment` (progressive cube capture + PMREM into `scene.environment`), `DayCycle` (time of day, sun direction, key light colour at `sunScale` 0.85 of the physical sun; `?time=<hours>`, `?daylength=<minutes>`). Needs the WebGPU backend; otherwise `World` falls back to the static skybox image and a hemisphere light (the `SunLight` cascades work on the WebGL backend too).
- **`src/PlayerController.js`** - First-person capsule player with BVH collision against terrain and ECS body meshes. WASD + PointerLock on desktop, nipplejs joysticks on mobile. The lock asks for raw mouse input (`lockPointer`, `unadjustedMovement`; a platform without it, Linux, gets the plain lock): with OS-adjusted input Chrome on Windows, Discord's desktop app included, now and then reports a huge bogus movement after warping the hidden cursor back, which snapped the view (a player's "rubberbanding"); `filterPointerSpikes` also drops any single movement over 600 px. `stats` counts dropped jumps, locks and time held still waiting for terrain, for the perf report. Its own mesh only casts a shadow (`maskNode` false, `maskShadowNode` true): the eye sits at the top of the rounded box, so camera shake (every rocket fired) lifted it out and flashed the box's top across the bottom of the screen.
- **`src/terrain/grid.js`** - Sparse chunk grid shared by server and client: keys, world config (bounds + implicit rock box), neighbour lookup, box queries.
- **`src/server/Terrain.js`** - Sparse chunk map with per-chunk Manifold booleans and fragment component extraction. Chunk bytes are the source of truth; the most recently used chunks keep a Manifold object and their decoded mesh up to a triangle budget (`RESIDENT_TRIS`, 250k: the whole castle fits), the rest are rebuilt by `manifoldOf()` on demand (`prepare()` gunzips them natively before a carve).
- **`src/server/Connectivity.js`** - Cross-chunk connectivity of solid (grounding, fragments) and air (which hollows are active and what to materialize).
- **`src/server/Physics.js`** - PhysX WASM setup, chunk colliders, and the ECS physics systems. The vendored `physx-js-webidl.wasm` has its initial memory patched from 64 MB to 16 MB (`tools/patch-wasm-memory.mjs`; it grows on demand).
- **`src/props/PropRegistry.js`** - Single source of truth for spawnable props (collider shape, size, GLTF url, menu entry).
- **`src/tools/*`** - Garry's Mod style tools (physgun, CSG brush, rope, weld, hinge). Tools send messages; the server mutates entities.
- **`src/net/codec.js`** - geometry codecs shared by both sides (brush soups, versioned chunk meshes with per-triangle materials, binary chunk frames).
- **`src/terrain/materials.js`** - terrain material palette; ids are tracked through Manifold booleans via reserved original IDs (see `docs/ecs.md`).

### Fort War (game mode): the game is called Undermine

The product name (page title, legal pages, HUD) is **Undermine**; "Fort War" stays the internal name of the mode and WorldParty the engine. A room whose world config carries `game` (sanitized by `src/game/rules.js`, written by `tools/gen-fortwar.mjs` into the manifest) runs Fort War: two teams, two forts with an underground vault each, and physics supply crates ("treasure"). The vaults start empty: neutral crates lie scattered over the level (`game.scatter`, checked by the generator to be in the open with a floor under them) and buried in sealed pockets (`game.caches`, `Supply.buried` until someone picks one up, so their markers stay hidden), so a round opens as a race to explore and turns into raids on what the other side brought home. Walk into a crate to carry it (one at a time: the pickup feedback follows `Player.carrying`, and walking into another while carrying says so); carry it into your vault to make it yours. A team scores units (`UNITS`): 100 per supply it holds (in its vault, or dropped and not yet returned) and 1 per crystal its players free from the ground (a glow rock shattering under a player's dig or blast: `applyCsg` records the carve's author `by` with its box, `GlowRocks.onTerrainChanged` credits each shattered rock to the first box that reaches it, `Game.creditCrystals` banks them in `Match.crystals`, kept if the player switches teams; `Player.score` is the units a player brought in, shown on the round-end screen). Most units when the 10 minute clock runs out wins (or as soon as one team holds every supply), then the round resets (terrain restored from `pristine:<key>` storage copies taken at import, supplies back out, everyone respawned). Rules and numbers live in `src/game/rules.js`; the server systems in `src/server/Game.js` (teams and spawns, rockets integrated against PhysX raycasts, grenades and bunker busters as props with a `Fuse`, explosions = `carveSphere` + velocity change on bodies + knockback and damage on players, the drill = `carveCapsule`, the convex hull of a 1.6 m sphere around the player resting at the feet and the same sphere 1.3 m ahead along the view, so one dig opens a walkable hole, digging down bores a shaft, and a tunnel dug walking forward has a smooth floor (separate spheres left a ridge between every two bites), supplies, rubble damage, rubble fading after 40 s asleep or past 110 fragments, the mason's stone budget earned by digging, the match, and votes). The local player's own rockets are predicted (`ProjectileRenderSystem.predict`, `GameClient.rocketHit`): the server only creates a rocket when `fire` arrives, so the shooter saw it a round trip plus up to a tick after the click (70-140 ms from this desktop); now it flies from the click with the server's ballistics, the server's rocket of ours is matched to it (oldest unmatched, same direction) and hidden, a terrain hit explodes at once on our side (the server's `explosion` with `by` = us within 3 m is then not shown again), a body or player hit parks the rocket for the server's verdict (600 ms), and anything the prediction got wrong falls back to the server's rocket and explosion. The predicted ball is shrunk within 6 m of the eye (`eyeScale`, about 4 degrees across): drawn at full size from its first frame 1.3 m out it covered a quarter of the screen's height, an orange flash on every shot. Grenades and busters are server props and still appear a round trip late. The client side is `src/client/GameClient.js` (created by `Main.onWorldChanged` when `world.game` appears): weapon tools in `src/tools/weapons.js` (a match hands out four: rocket, drill, mason, physgun, keys 1-4; the grenade and buster still work but are not handed out; the grapple is no tool but the right mouse button with any of them, `Grapple`, and a Hook button on phones via `SpawnMenu.setExtraMobileActions`; the mason's shape and the physgun's freeze moved to F; the drill shows no preview), HUD in `GameHud.js` (kept sparse: the health bar alone in the top left, the score bar, weapon slots at the bottom (the selected one framed, the mason's showing its stone; tapping or clicking one selects it, which is how a phone switches weapons) and no tool name anywhere (`SpawnMenu.setGameHud` hides the sandbox tool label and tool button; Q still opens the menu); bottom right the treasure finder, the nearest neutral crate's distance and how far above or below it is within `SUPPLY.senseRange`, else the only instruction, "Find the Treasure."; it replaced a blinking, beeping light; a scoreboard while Tab is held or after a tap on the score bar (phones): a column per team with its units, players best first with units, crystals, crates home, kills and deaths, the local player highlighted and the dead dimmed, rebuilt at most every 250 ms when something on it changed, names escaped; the FPS panel only with `?stats=1`; HUD texts are written only when they change), synthesized sound in `Sfx.js`, projectile / supply / fuse / explosion visuals in `gameSystems.js`. The sandbox tool bar stays hidden until the first full update says what kind of room this is (`Main.roomKnown`). Player movement stays client-authoritative; the server sends `spawn`/`respawn` (teleport), `hit` (knockback), `explosion` (effects; `by` is the shooter) and `event` (feed) and trusts the client, so there is no anti-cheat by design; a position report still in flight from before a respawn teleport is ignored by the kill plane for `KILL_GRACE_MS`, or falling out of the world killed twice. Client messages: `fire {weapon, origin, dir, power}`, `dig`, `build {shape, position, quaternion}`, `respawn`, `jointeam`, `heartbeat` (every 5 s while there was input in the last minute), `vote {action}`; during a match `spawnprop` is ignored (no props from the menu; the Props button is hidden), the physgun cannot grab supplies, a dead player's holds are released (`Game.kill`; the client's `PhysGunTool.release` too) and their `physgun_move` ignored, and `reset`/`setgravity` are ignored: admin actions (`VOTE.actions`: reset the map, end the round, swap teams) are voted on from the V panel or `/vote <action>` in chat, pass with a majority of the *active* players (a heartbeat within 90 s; AFK players do not count, so a lone player's vote goes through at once), and the running vote is in `Match.vote`. The level ("Twin Forts", 2fort-like) is generated procedurally: forts with walls, towers, a wooden gate, a walkway, an underground vault reached by a ramp; a gorge with a destructible bridge and plaza; sewers from each vault to the gorge; a high road over a rock arch and a cave route through a tube on the flanks; sealed pockets of neutral supplies to dig for. Carrying a supply home while underground (outside both vaults) for 4 s earns a bonus crate. Glow rocks light the tunnels: a virtual field of luminous pebbles fills the ground below `surfaceY - 0.9` (`game.glowRocks: {seed, cell, density}`, a rock in about half the 1.1 m cells, radius 0.06-0.16, decided by a hash in `rules.js` `virtualRock`, so nothing is listed per rock); `src/server/GlowRocks.js` materializes one as a `GlowRock` entity (static, embedded, CSG never touches it: it is not terrain) when a carve's region or the lazy scan of chunks near players finds air meeting it under a ceiling (exposure = fraction of 19 sample points in air, by ray parity against a three-mesh-bvh BVH of the chunk mesh, cached per version; a closest-point query skips rocks nowhere near a surface; a ray straight up that escapes means a crater or a cliff, no rock; a rock found all in air that was not in solid before the carve never existed). At exposure 0.97 it shatters: the entity goes, the cell remembers, and clients get `glowpop {rocks: [[x, y, z, colour]]}` (a burst of shards, `GlowSparkFx`, and a tinkle). They used to become sphere bodies, which filled every fresh tunnel with pebbles (a drill bite frees the half dozen inside its sphere). `newRound` puts them all back. The client instances them with an emissive material; their light is baked into the terrain's vertex GI where that runs (see `TerrainGI.js` above), and otherwise (`?vgi=0`, no WebGPU) comes from `src/client/GlowLighting.js` (twelve point lights on the nearest rocks lit almost nothing): each exposed rock is splatted on the CPU into a 0.5 m 3D texture around the camera (80x32x80, 64x32x64 on mobile; RGB colour sum and the mean direction to the rocks), and a light node adds colour * max(0, 1/4 + 3/4 n.d) to the indirect diffuse of every standard material, two texture reads per pixel for any number of rocks. A rock's light stands 35 cm out of the wall toward its open side (36 coarse rays) and casts a 12x12 octahedral map of rays from there against the chunk BVHs; a texel takes the light only if it is no further than the wall in its direction (plus 0.45 m of slack, fading over 0.5 m), which keeps it out of the tunnel next door. Splats are additive, so a change subtracts the rock's old record and adds the new one and uploads only the touched z slices (a Data3DTexture given `layerUpdates`, which r186's WebGPU backend honours); when the camera leaves the window's middle, a second accumulator is filled for the new window over a few frames and swapped in. Idle it costs 0.1 ms a frame; while digging, the occlusion maps around the carve are recomputed within a 2 ms budget. The probe bake mutes it (`Main.muteDuringProbeBake`). `?glow=0` turns it off, `?glow=<n>` sets the intensity (35). Sound effects are all WebAudio synthesis in `src/client/Sfx.js` (primitives in `Synth`, a `SOUNDS` table that plays live or renders into an OfflineAudioContext via `Sfx.renderOffline(name, seconds)` for testing, distance and pan from the camera, a stateful loop for the grapple reel (the drill is a pickaxe strike per dig, `pick`: short and bright; a drill motor loop with a deep bite read as terrifying), a master bus with a tanh safety clipper, mute on M persisted in localStorage). The music is "Gold Rush Heist" (`assets/music/gold-rush-heist.mp3`, made with Suno; `src/client/MusicTrack.js`): an `<audio>` element streamed into the effects' master bus (mute applies; decoding it whole would hold ~56 MB on a phone), looped at bus gain 0.14 so the mastered track (-15.9 LUFS) plays near -35 dB RMS, with a 4 dB dip around 2.5 kHz, so a voice call stays clear over it; it fades in, drops to half behind a 600 Hz lowpass while dead, and pauses while the page is hidden. The Worker serves `/assets/music/*` itself (`rangedAsset` in `src/server.js`, listed in `run_worker_first`): static assets answer a Range request with the whole file, Safari and iOS want byte ranges for media, and Discord's CSP rules out a blob URL. `?music=score` plays the earlier generative score instead (`src/client/Music.js`: 92 BPM, D Mixolydian like every jingle and the treasure beep; pad, bell arpeggio, drums, lead and a last-minute tick on separate gains, driven by carrying, the clock, nearby explosions and death; -33 dB RMS at its default), `?music=0` no music. The effects use no audio files; the track is the one, served from the app's own origin (the Discord CSP is `default-src 'self'`). Test the server side without a browser the usual way (`node tools/profile/build.mjs`, then a harness that connects fake connections and calls `onMessage`).

### Discord Activity

The site doubles as a Discord Activity (`src/client/Discord.js`, `@discord/embedded-app-sdk`). Discord loads it in an iframe at `https://<client id>.discordsays.com/` through its proxy with a root URL mapping (`/` → `worldparty.makeshifted.workers.dev`); the proxy's CSP allows the whole app origin for fetch and WebSocket and blocks everything external, so nothing in the client may load from another host there (the Draco decoder on gstatic and GLBs by foreign URL are the exceptions, and they just fail). No `/.proxy` prefix is needed any more. Inside Discord the room is `discord-<activity instance id>` (everyone who launched the activity from the same channel shares it), the first player in an empty room uploads `assets/worlds/fortwar.json` (`Main.importIfEmpty`: the lowest connection id among the players in the first full update without `world.game`), and the player is named after the Discord user: the SDK's `authorize` code is exchanged on the Worker (`POST /api/discord/token`, `run_worker_first` covers `/api/*`) using the `DISCORD_CLIENT_SECRET` secret (`npx wrangler secret put DISCORD_CLIENT_SECRET`); without it players stay anonymous. The client id is read from the proxy hostname (`DISCORD_CLIENT_ID` in `wrangler.jsonc` overrides it on the Worker; both are set for the real app). `terms.html` and `privacy.html` (copied into `public/` by the build) are the Terms of Service and Privacy Policy Discord's app verification links to. `?discord=mock` runs the same path in a normal browser with the SDK's mock (instance `123456789012345678`, user `mock_user_username`). Developer Portal setup: enable Activities, URL mapping `/` → the Worker host, OAuth2 redirect `https://127.0.0.1`, both install contexts; then launch from the channel's activity shelf.

### Units and gravity

World units are metres (10 m chunks, 1 m props, a 2 m player capsule) but nothing falls at 1 g (`src/gravity.js`): real gravity at this scale reads as slow motion, so the player controller is tuned at `PLAYER_GRAVITY` (8 g) and rigid bodies fall at `DEFAULT_BODY_GRAVITY` (30 m/s², chosen by feel: 60 was too fast with Fort War's crates and rubble, 2 g too floaty on the castle). Under that gravity a falling body covers over 2 m per 30 Hz step, so every dynamic body has speculative CCD (without it a cannonball dropped from the walls goes straight through the ground), the shared material's restitution is 0.05 so things land dead, and sleep thresholds scale with gravity (`PxTolerancesScale.speed`, `fragmentSleepThreshold`), otherwise contact jitter keeps whole piles awake. A room overrides the body gravity with `world.gravity` (set from the client with `?gravity=<m/s²>` → `setgravity`, persisted with the world config, replaced by an import, reported in chat); `Physics.setGravity` wakes every body so piles re-settle.

### Terrain System

The world is a sparse grid of 10-unit chunks keyed `"x,y,z"` (chunk x covers [10x, 10x+10)). A per-room world config (`src/terrain/grid.js` `DEFAULT_WORLD`, stored under the `world` key, sent in full updates) gives the bounds and the box of implicit rock; the sandbox default is a 100 m cube centred on the origin, solid below y=0. Unstored chunks are implicit (rock inside that box, air elsewhere); only CSG-modified chunks are stored, as indexed meshes versioned by content hash. A `csg` message lists the overlapped chunk keys plus the brush soup and transform; the server runs the boolean in Manifold (clipping to the chunk only for additions), re-encodes the chunk (uncompressed layout, whose FNV hash is the version; the gzip runs later with the platform's native `CompressionStream`, `Terrain.compress()`, never on the carve path) and pushes it to every holder as a binary WebSocket frame right away: a delta against the version they hold (`encodeChunkDelta`, typically a few KB: old vertices and triangles by reference, new ones inline, exact reconstruction so deltas chain) or the full bytes when the change is large or the holder's version is unknown. Grounding, fragment shedding, colliders and activity run in a timer callback once the frames are out (`settleNow`), so carving latency is the boolean plus the encode. Unsupported solid becomes `RigidBody{shape:'trimesh'} + FragmentMesh` entities; their collider is a compound of convex hulls (`FragmentMesh.hulls`, built by `Terrain.fragmentHulls` from ~1.5 m cells of the fragment, at most 24) because a dynamic SDF triangle mesh costs 1 to 3 ms of PhysX per awake fragment per tick (a woken pile of rubble used to saturate the 33 ms tick and every carve queued behind it). Fragments stored without hulls get them on load (`upgradeFragments`); the SDF mesh remains the fallback when no hull cooks. Updates otherwise carry only `{key: version}` and clients fetch missing versions over HTTP (`/parties/main/<room>/chunk/<x,y,z>?v=<version>`, served immutable and cached at the edge by the Worker). The client `TerrainMirror` keeps one `Mesh` (with its own BVH) per held chunk under a group, for collision, tool raycasts and the probe grid's inside-solid test (`terrain.group`, not drawn: the Raycaster ignores `visible`); what is drawn are batch meshes (`renderGroup`): a region of 4x2x4 chunks is one or more plain meshes of at most 32k triangles concatenated from its chunks' geometries (one material, world space). Twin Forts is 356 chunk meshes averaging 32 triangles, and every draw costs the same CPU however small: batching took a frame from ~800 draw calls (with the shadow cascades) to ~130, render CPU from 7 to 1.7 ms and a probe bake from 12 to 4 ms per probe on this desktop. Batches draw each chunk's refined render geometry from TerrainGI (`TerrainMirror.render`, `setRenderGeometry`; indexed, with a `rec` attribute) when it has one, else its collision geometry. A chunk that changes leaves its batch's draw at once (its index range is zeroed and the index buffer re-uploaded) and draws as its own mesh ("hot"), so a carve shows with no extra latency; 2 s after the last change in a batch it is rebuilt as a fresh Mesh including the chunk (~1.5 ms for a full 31k triangle castle batch). `?batch=0` draws one mesh per chunk. An earlier attempt with three's `BatchedMesh` showed mismatched triangle indices on WebGPU (commit 533df12), which is why this uses plain meshes. Grounding and loading are decided by `src/server/Connectivity.js`: solid and air islands per chunk (`decomposeParts`: Manifold's `decompose()` splits a cavity enclosed inside one chunk off as a negative-volume part, which would then be shed as an ungrounded island and the cavity filled; such parts are composed back into the part around them), face footprints rasterized on a 16x16 grid, union-find across chunks. Per-chunk summaries are persisted (`summary:<key>`, adopted when the version matches) so a room starts without rebuilding any manifold; mesh colliders are cooked nearest to players and awake bodies first, a few per tick. Unsupported solid becomes fragments (merged across chunks); terrain is only held and collided where it faces an air component containing a player or an awake body (sleeping bodies keep nothing loaded; removing or restoring a collider does not wake what rests on it, only a geometry change wakes the bodies reaching into that chunk, `Physics.wakeNear`), so buried rock and empty sealed caves cost nothing. Updates carry `chunks`/`rock`/`cull` maps and the client holds only what it is told to.

### Chunk planes and zero-thickness sheets

Nothing in a level may lie exactly on a chunk plane (a multiple of 10 on any axis) as a solid/air interface: when a solid only *touches* a chunk cube from outside (the ground's top at y = 0 under the chunk above it, a wall face on x = -50), Manifold's intersection leaves a zero-thickness sheet of coincident, opposite-facing triangles in the air-side chunk instead of nothing. The sheet is invisible until a carve retriangulates it, when its pieces stretch across the hole and only a second carve removes them (this was the "repositioned triangles / slivers over holes" bug; 10 of 60 rockets reproduced it). `tools/gen-fortwar.mjs` therefore translates the whole design by 0.1 m on every axis (config coordinates included) and `tools/import-world.mjs` seats models at y = 0.1 with the footprint centre at (0.13, 0.13). Worlds imported before 2026-10-18 carry the sheets until re-imported. A solid that *crosses* a plane is fine. `/tmp`-style checks: triangles on a boundary plane facing into the chunk cannot be real geometry.

### World Import

`tools/import-world.mjs` turns any GLB into terrain without assuming watertight or consistently oriented input, following the order 3D-printing slicers repair meshes in. The default `--mode exact` works per GLB primitive and per edge-connected component (`tools/lib/repair.mjs`): weld vertices within `--weld`, drop degenerate and duplicate triangles, orient faces consistently and outward, fill boundary loops shorter than `--hole`, thicken anything still open into a shell of `--shell` metres (retrying thinner), reject results that cross themselves, and flip inside-out solids. Closed components keep every triangle, UV and material; `Manifold.union` resolves the components against each other, like Cura's union of overlapping volumes. Components that cannot be closed (non-manifold edges, self-crossing shells) fall back to a level set of their own with UVs projected from their triangles. `--mode shell|winding|both|parity` instead level-sets the whole soup (shell: solid within `--shell` of any surface; winding: generalized winding number). The result is simplified, split by exact chunk-cube intersection, and written as `{world, chunks: {key: {version, bytes}}}` with the source materials (exact base colours, base colour textures written next to the manifest). With the default floor, an exact ground slab sits under the model on implicit rock. The client uploads manifests in `import_begin` / `import_chunks` / `import_end` messages.

### Networking Protocol

JSON over WebSocket. Client → server: `player`, `ping` (answered with `pong` at once: the ping in the corner), `perf` (below), `csg`, `import_begin/chunks/end`, `spawnprop`, `physgun_grab/move/release/freeze`, `createjoint`, `removejoint`, `deletebody`, `model`/`select`/`deselect`/`deletemodel`, `chat`, `reset`, `setgravity`, and in Fort War `fire`, `dig`, `build`, `respawn`, `jointeam` (`name` renames the player; Discord sessions send it on connect). Server → client: `fullupdate` / `partialupdate` with `entities`, `removed`, `chunks` (`{key: version|null}`), `rock` (`{key: faceMask}`), `cull` (`{key: faceMask}`), `serverTickMs` (the tick's duration: only meaningful in the Node harness, since Cloudflare's clock stands still within an event) and `serverGapMs` (the longest gap between tick starts over the last second: the corner shows "server lag" above 60 ms), plus binary chunk frames (type 1 full, type 2 delta with a base version); `chat`, and in Fort War `spawn`, `respawn`, `hit`, `explosion`, `event`. Note `Date.now()` does not advance during synchronous work on Cloudflare, so server-side ms figures are only meaningful in the Node harness.

## Memory budget

A Durable Object gets 128 MB. Measure with `node tools/profile/build.mjs && node --expose-gc tools/profile/mem.mjs` / `heap.mjs` / `heap-steps.mjs`; the `World ready` log line prints both WASM heap sizes. Emscripten heaps never shrink, so peaks matter: the castle (73 chunks, 196k triangles) starts warm at 16 MB Manifold, grows to about 33 MB as chunks are carved and stay resident (`RESIDENT_TRIS`), and peaks at 33 MB on a cold settle of the whole world (import or no stored summaries), which runs under the smaller `COLD_RESIDENT_TRIS` budget; PhysX 16 MB, JS about 35 MB. Keep this in mind for anything that holds manifolds for many chunks at once (the settle loop releases each chunk's islands as soon as its last fragment is built for exactly this reason). `WARM=1 node tools/profile/replay.mjs ...` measures the production path (second start adopting stored summaries).

## Notes

- Source uses bare specifier imports (e.g., `'three'`, `'three-mesh-bvh'`) resolved by esbuild during bundling.
- The server runs three.js headlessly for CSG computations (no rendering).
- Geometry data is serialized as gzip-compressed base64 (position arrays only), using fflate for compression.
- Server guards against double-disconnect (onClose/onError both call onDisconnect) and against a replaced socket closing late (a reconnect with the same id). A dropped player is kept aside for `RESUME_MS` (60 s, `lingering`): PartySocket reconnects with the same id, and the player comes back as it was (same team, stats and position, no spawn; `Game.onResume`, which starts a new round's stats if one began meanwhile). Before, every network blip and every deploy teleported everyone back to a spawn point.
- Perf reports (`src/client/PerfReport.js`): every 20 s each client sends frame rate, longest frame, frames over 50 ms, ping, reconnects, dropped mouse jumps, time held still for terrain, chunk deltas that did not apply, teleports, backend, GPU, client (Electron/Discord/Chrome version and OS), canvas size; the server whitelists the fields (`PERF_FIELDS`), adds its longest tick gap, logs a `perf {...}` line (visible in `wrangler tail`) and keeps the last 300 in storage, served at `GET /parties/main/<room>/perf`. No names: a connection id prefix. Use it to look at a player's lag after the fact (the privacy policy mentions it).
- Static assets (`index.html`, `assets/`, the bundle) are copied into `public/` by the build and served by Workers Assets; the Worker only sees `/parties/*`.
